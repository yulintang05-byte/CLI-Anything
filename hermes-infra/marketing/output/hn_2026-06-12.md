# Show HN: Hermes – A Rust terminal client for Claude

---

## HN Post Body

I spend most of my day in tmux on remote boxes, and getting Claude into that workflow has been awkward. claude-code is genuinely good inside VS Code or JetBrains, but the moment you're SSH'd into a build server or want to pipe a compiler error into a model and pipe the answer into a file, you're fighting the tooling. So I built Hermes, a standalone terminal client for Claude. Upfront: it's a paid product, $12/mo (Pro) or $29/mo (Ultra), no free tier. I'd rather you know that in sentence three than after an install.

The core design goal was a hard latency budget: first token rendered in under 50ms after it arrives on the wire, and steady-state rendering that never drops behind the stream. That's why it's Rust. The streaming path is zero-copy where possible — SSE chunks are parsed in place and written to a damage-tracked TUI buffer without intermediate allocations on the hot path. No GC means no pause spikes mid-stream, which matters more than you'd think: a 30ms GC stall during token rendering is visually obvious in a way it isn't in a web UI. The TUI is purpose-built rather than wrapping a generic framework, so redraws only touch dirty cells.

On cost: Hermes batches and caches requests aggressively. If you re-run a command with overlapping context (very common when iterating on a prompt or debugging the same file), the prefix is cache-hit rather than re-sent, which Anthropic prices at a steep discount. In my own usage this cut effective token spend by roughly 40% versus naive request-per-invocation. Your mileage will vary with workload — I'm happy to share methodology in the comments.

How it differs from claude-code: claude-code is the better choice if you live in an editor and want deep integration — inline diffs, file context, that whole loop is excellent and I use it. Hermes is for when the terminal *is* the environment. It reads stdin, writes clean stdout, exits with meaningful codes, so you can do things like `make 2>&1 | hermes "explain this failure"` or wire it into a git hook. It works over SSH, inside tmux, in CI if you're feeling brave.

Install is one line:

`curl -fsSL https://hermes.sh/install.sh | bash`

(Yes, I know — the script is short and readable, please do read it first. Checksummed binaries are also on the site.)

You bring your own Anthropic API key; the subscription pays for the client, the caching layer, and updates. Purchase and docs at https://whop.com/hermes. Honest feedback welcome, especially on the pricing model — I went back and forth on it a lot.

### Comment 3
**HN commenter:** "Faster streaming" — faster than what, exactly? The bottleneck is Anthropic's API, not your client. Token generation speed dominates everything.

**Founder response:** You're right that generation speed dominates end-to-end latency, and I should be careful with claims. What Hermes controls is wire-to-screen time and rendering consistency — no dropped frames or stutter on long streams, which some Node-based clients do exhibit under load. The bigger practical win is actually the prefix caching reducing time-to-first-token on repeated context, not raw throughput.

### Comment 4
**HN commenter:** What happens to my prompts in your "caching layer"? Is my code going through your servers?

**Founder response:** Important question. The cache is local-first: prefix hashing and dedup happen on your machine, and requests go directly to Anthropic with your key. The Ultra tier offers optional team-shared caching which does route through our infra — that's opt-in, documented, and encrypted at rest, but if that's a dealbreaker the Pro tier never touches our servers for inference traffic.

### Comment 5

**Founder response:** Honestly, it was the fastest way to ship subscriptions without building billing myself, and I wanted to validate demand before investing in Stripe + a license server. It's a legitimate criticism — the optics aren't great for this audience. If there's traction, direct billing is the first infrastructure project on the list.

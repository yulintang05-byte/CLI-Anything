# I built a Rust terminal for Claude AI — here's what I learned

## Why I built it

I spend most of my day in a terminal over SSH. My dev box is a headless machine in a closet, and my "IDE" is tmux + helix + a pile of shell scripts. Every AI coding tool I tried assumed the opposite: a local GUI, an editor extension, an Electron app. The Claude web UI is fine, but copy-pasting code between a browser and a remote shell got old fast.

What I actually wanted was simple to describe and annoying to build: a Claude client that behaves like a proper Unix citizen. Something I could run interactively in a TUI when I want a conversation, but also pipe into. `cat error.log | hermes "what's failing here"` should just work. It should survive flaky SSH connections, render fast on a 300ms-latency link, and not eat my scrollback.

So I built Hermes. It's written in Rust, it's a commercial product (more on the pricing later — I know that's a loaded topic on Dev.to), and building it taught me more about async streaming and terminal emulators than I expected to learn this year.

## The architecture

The shape of it:

```
 stdin / args
      │
      ▼
 ┌─────────────┐     ┌──────────────┐     ┌─────────────────┐
 │  CLI parser  │────▶│ Session mgr  │────▶│ Anthropic API   │
 │  (clap)      │     │ (SQLite)     │     │ (SSE / reqwest) │
 └─────────────┘     └──────────────┘     └─────────────────┘
                            │                      │
                            ▼                      ▼
                     ┌──────────────┐     ┌─────────────────┐
                     │ prompt-cache │     │ stream decoder   │
                     │ bookkeeping  │     │ (frame buffer)   │
                     └──────────────┘     └────────┬─────────┘
                                                   ▼
                                          ┌─────────────────┐
                                          │ TUI renderer     │
                                          │ (crossterm)      │
                                          └─────────────────┘
```

Everything runs on tokio. The API layer uses reqwest with hyper underneath for SSE streaming — Claude's API streams responses as server-sent events, and getting those rendered token-by-token without jank is most of where the engineering time went.

The piece I'm happiest with is the SQLite session cache. Each conversation gets a row with message history plus metadata about what prefix has been sent before. Anthropic's prompt caching gives you discounted tokens when you resend an identical prefix within the cache TTL, so Hermes tracks cache breakpoints across *separate CLI invocations*. If you run `hermes -c "follow-up question"` thirty seconds after your last command, the prior context hits the server-side cache instead of being billed at full price. That only works because the state lives in SQLite rather than in-process — the process is dead between invocations.

Crossterm handles raw mode and rendering. I deliberately didn't use a full TUI framework like ratatui for the streaming view; I wanted line-oriented output that plays nice with scrollback and `tee`. The interactive mode uses an alternate-screen view, but pipe mode is plain stdout with ANSI stripped if `!isatty`.

## The trickiest parts

### Partial SSE frames across TCP segments

This one bit me in week one. SSE events are delimited by `\n\n`, but TCP doesn't care about your framing. A chunk from the stream can end mid-event, mid-line, or — my favorite — *between the two bytes of `\r\n`*. My naive first version split each chunk on `\n\n` independently and silently dropped tokens whenever a frame straddled a boundary. It worked perfectly on localhost and failed constantly over real networks, which is the worst kind of bug.

The fix is the obvious one in retrospect: a persistent buffer that only drains complete events.

```rust
struct SseDecoder {
    buf: Vec<u8>,
}

impl SseDecoder {
    fn feed(&mut self, chunk: &[u8]) -> Vec<SseEvent> {
        self.buf.extend_from_slice(chunk);
        let mut events = Vec::new();

        // Only consume up to the last complete event boundary.
        while let Some(pos) = find_event_boundary(&self.buf) {
            let raw: Vec<u8> = self.buf.drain(..pos + 2).collect();
            if let Some(ev) = parse_event(&raw) {
                events.push(ev);
            }
        }
        events
    }
}

fn find_event_boundary(buf: &[u8]) -> Option<usize> {
    // Handle both \n\n and \r\n\r\n. Anthropic sends \n\n today,
    // but proxies have rewritten this on me before.
    buf.windows(2).position(|w| w == b"\n\n")
        .or_else(|| buf.windows(4).position(|w| w == b"\r\n\r\n").map(|p| p + 2))
}
```

The comment about proxies is from experience: a user behind a corporate proxy reported garbled output, and the proxy was normalizing line endings. Defensive parsing here is not optional.

### Raw-mode cleanup on panic

If your program panics while the terminal is in raw mode with the alternate screen enabled, the user gets a terminal that doesn't echo keystrokes and looks broken. They'll blindly type `reset` and curse your name. Rust panics unwind through `Drop`, so the fix is a guard that restores the terminal no matter how you exit:

```rust
struct RawModeGuard;

impl RawModeGuard {
    fn enter() -> io::Result<Self> {
        crossterm::terminal::enable_raw_mode()?;
        crossterm::execute!(io::stdout(), EnterAlternateScreen)?;
        Ok(RawModeGuard)
    }
}

impl Drop for RawModeGuard {
    fn drop(&mut self) {
        // Ignore errors — we're possibly mid-panic and can't do
        // anything useful about them anyway.
        let _ = crossterm::execute!(io::stdout(), LeaveAlternateScreen);
        let _ = crossterm::terminal::disable_raw_mode();
    }
}
```

Two gotchas. First, `Drop` doesn't run on `std::process::exit` or on abort-on-panic builds, so I also install a panic hook that does the same cleanup before printing the panic message — otherwise the message itself renders mangled in raw mode. Second, on Windows, crossterm's raw mode interacts with the legacy console differently than Windows Terminal: resize events arrive on a different path, and I had a bug where `Ctrl+C` was delivered as a key event in raw mode (correct) but my handler only listened for the signal (wrong). Windows users got an unkillable process. Test on conhost, not just Windows Terminal.

### Rendering under backpressure

Tokens arrive in bursts — sometimes 40 SSE events in a few milliseconds. Writing to the terminal for every event made rendering the bottleneck, especially over SSH where each write can become a packet. The stream would visibly stutter because the network task was waiting on terminal I/O.

The fix was decoupling: the decoder task pushes tokens into an unbounded channel, and a render task drains *everything available* on each tick (~16ms) and writes one batched, buffered update. Burst of 40 tokens? One write. The perceived smoothness improved dramatically and SSH bandwidth dropped because escape sequences get coalesced. The lesson: never let your network reader block on your renderer, in either direction.

## Live demo: installing and using Hermes

Install:

```bash
curl -fsSL https://hermes.sh/install.sh | bash
```

(Yes, curl-pipe-bash. The script is short and readable, and there's a manual install path in the docs if that's not your thing — I get it.)

Interactive use:

```bash
$ hermes "explain what this lifetime error means" --file src/parser.rs

The error occurs because `tokens` borrows from `input`, but the
function signature promises a 'static return. You have two options:

1. Return owned data: change `Vec<&str>` to `Vec<String>`
2. Tie the lifetimes: `fn parse<'a>(input: &'a str) -> Vec<&'a str>`

Given the call sites in this file, option 2 avoids allocations...
```

And the part I actually built this for — piping:

```bash
$ git diff HEAD~1 | hermes "write a conventional commit message for this" --plain
fix(decoder): buffer partial SSE frames across chunk boundaries

$ hermes "list the public functions in this file as JSON" --file lib.rs --plain | jq '.[] | .name'
"parse_event"
"feed"
"find_event_boundary"
```

`--plain` strips ANSI and disables the TUI, so output composes with anything.

## Is it worth $12/mo?

Honest answer: it depends on how you work.

Hermes Pro is $12/mo and Ultra is $29/mo (higher rate limits, longer session retention). That's on top of being a Claude product, so I want to be upfront about who should *not* buy it: if you mostly chat with Claude casually, the free web UI is genuinely good and you should use that. If you live in VS Code, Anthropic's own extension ecosystem probably fits you better.

Hermes makes sense if you're terminal-native: you work over SSH, you want AI in shell pipelines and scripts, or you want the prompt-cache bookkeeping handled so repeated context doesn't cost full price on every invocation. For me the cache handling alone changed how often I reach for it — asking a follow-up question stopped feeling expensive.

It's at [whop.com/hermes](https://whop.com/hermes) if you want to look. No hard sell — the free web UI exists and it's good.

## What's next

Three things on the roadmap:

1. **MCP support** — letting Hermes act as an MCP client so it can use local tools (filesystem, git) during a conversation.
2. **Session export/import** — sessions as portable JSON, so you can move a conversation between machines or check one into a repo.
3. **Vim-style keybindings** in the interactive TUI, because the issue tracker has spoken.

If you try it and something breaks — especially on Windows, especially over weird proxies — please file a bug. The SSE proxy story above came from a user report, and it made the product better for everyone. The strangest terminal configurations always find the best bugs.
